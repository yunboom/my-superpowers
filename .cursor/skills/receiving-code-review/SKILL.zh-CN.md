# 接收代码审查

## 概述

代码审查需要技术评估，而非情绪表演。

**核心原则：** 实施前先验证。假设前先询问。技术正确性优先于社交舒适度。

## 响应模式

```
收到代码审查反馈时：

1. 阅读：完整阅读反馈，不急于反应
2. 理解：用自己的话复述需求（或提问）
3. 验证：对照代码库实际情况检查
4. 评估：对本代码库来说技术上合理吗？
5. 响应：技术性确认或有理有据的反驳
6. 实施：逐项实施，每项测试
```

## 禁止的回应

**绝不：**
- "你说得太对了！"（明确违反 CLAUDE.md）
- "好观点！" / "优秀的反馈！"（表演性的）
- "让我现在就实施"（验证之前）

**应该：**
- 复述技术需求
- 提出澄清问题
- 如果有误，用技术理由反驳
- 直接开始工作（行动 > 语言）

## 处理不清晰的反馈

```
如果有任何条目不清晰：
  停下 - 不要实施任何东西
  对不清晰的条目提问澄清

原因：条目可能相互关联。部分理解 = 错误实施。
```

**示例：**
```
你的人类搭档："修复 1-6"
你理解 1、2、3、6。对 4、5 不清楚。

❌ 错误：先实施 1、2、3、6，稍后再问 4、5
✅ 正确："我理解条目 1、2、3、6。在继续之前需要对 4 和 5 进行澄清。"
```

## 按来源分类处理

### 来自你的人类搭档
- **可信** - 理解后实施
- **仍需提问**如果范围不清
- **不做表演性认同**
- **直接行动**或技术性确认

### 来自外部审查者
```
实施之前：
  1. 检查：对本代码库来说技术上正确吗？
  2. 检查：会破坏现有功能吗？
  3. 检查：当前实现的原因是什么？
  4. 检查：在所有平台/版本上都有效吗？
  5. 检查：审查者是否理解完整上下文？

如果建议看起来有误：
  用技术理由反驳

如果无法轻易验证：
  如实说明："我无法在没有 [X] 的情况下验证这一点。我应该 [调查/询问/继续]？"

如果与你的人类搭档之前的决定冲突：
  停下来先与你的人类搭档讨论
```

**你的人类搭档的规则：** "外部反馈 - 保持怀疑，但仔细检查"

## YAGNI 检查"专业"特性

```
如果审查者建议"正确实现"：
  在代码库中 grep 实际使用情况

  如果未使用："这个端点没有被调用。删除它（YAGNI）？"
  如果有使用：那就正确实现
```

**你的人类搭档的规则：** "你和审查者都向我汇报。如果我们不需要这个功能，就不要添加它。"

## 实施顺序

```
对于多条目反馈：
  1. 首先澄清任何不清晰的内容
  2. 然后按此顺序实施：
     - 阻塞性问题（崩溃、安全）
     - 简单修复（拼写、导入）
     - 复杂修复（重构、逻辑）
  3. 逐个测试每个修复
  4. 验证无回归
```

## 何时反驳

在以下情况反驳：
- 建议会破坏现有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对本技术栈来说技术上不正确
- 存在历史/兼容性原因
- 与你的人类搭档的架构决策冲突

**如何反驳：**
- 使用技术理由，而非防御性态度
- 提出具体问题
- 引用工作中的测试/代码
- 如涉及架构问题，让你的人类搭档参与

**如果不便当面反驳的信号：** "Strange things are afoot at the Circle K"

## 确认正确的反馈

当反馈确实正确时：
```
✅ "已修复。[简要描述变更内容]"
✅ "好的发现 - [具体问题]。已在 [位置] 修复。"
✅ [直接修复并在代码中展示]

❌ "你说得太对了！"
❌ "好观点！"
❌ "感谢你发现了这个！"
❌ "感谢 [任何内容]"
❌ 任何感谢表达
```

**为什么不感谢：** 行动说明一切。直接修复就好。代码本身就表明你接收了反馈。

**如果你发现自己即将写"感谢"：** 删掉它。改为说明修复内容。

## 优雅地纠正你的反驳

如果你反驳后发现自己错了：
```
✅ "你是对的 - 我检查了 [X]，它确实 [Y]。现在实施。"
✅ "验证后确认你是正确的。我最初的理解有误，因为 [原因]。正在修复。"

❌ 冗长的道歉
❌ 为什么要反驳做辩护
❌ 过度解释
```

客观陈述纠正，然后继续。

## 常见错误

| 错误 | 修正 |
|------|------|
| 表演性认同 | 陈述需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量操作不测试 | 逐项实施，每项测试 |
| 假设审查者正确 | 检查是否会破坏功能 |
| 回避反驳 | 技术正确性 > 舒适度 |
| 部分实施 | 先澄清所有条目 |
| 无法验证仍继续 | 说明限制，请求指导 |

## 真实示例

**表演性认同（错误）：**
```
审查者："删除遗留代码"
❌ "你说得太对了！让我删除那个..."
```

**技术验证（正确）：**
```
审查者："删除遗留代码"
✅ "检查中...构建目标是 10.15+，这个 API 需要 13+。为了向后兼容需要保留遗留代码。当前实现的 bundle ID 有误 - 修复它还是放弃 pre-13 支持？"
```

**YAGNI（正确）：**
```
审查者："实现带数据库、日期筛选、CSV 导出的正式指标跟踪"
✅ "搜索了代码库 - 没有任何地方调用这个端点。删除它（YAGNI）？还是有我遗漏的使用场景？"
```

**不清晰的条目（正确）：**
```
你的人类搭档："修复条目 1-6"
你理解 1、2、3、6。对 4、5 不清楚。
✅ "理解 1、2、3、6。在实施前需要对 4 和 5 进行澄清。"
```

## GitHub 评论回复

在 GitHub 上回复内联审查评论时，在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而非作为顶层 PR 评论。

## 底线

**外部反馈 = 需要评估的建议，而非需要执行的命令。**

验证。质疑。然后实施。

不做表演性认同。始终保持技术严谨。
