# 需求文档审查 Prompt 模板

派遣需求文档审查子代理时使用此模板。

**用途：** 验证需求文档是否完整、一致，并已准备好进入设计或 HLD 阶段。

**触发时机：** 需求文档写入 docs/specs/yyyy-MM-dd-REQ-{id}/{topic}/requirements.md 之后

```
Task tool (general-purpose):
  description: "Review requirements document"
  prompt: |
    你是一个需求文档审查员。验证此需求文档是否完整且已准备好进入下一阶段（HLD 或详细设计）。

    **待审查需求：** [REQUIREMENTS_FILE_PATH]

    ## 检查项

    | 类别 | 检查内容 |
    |------|---------|
    | 功能边界 | 功能边界是否清晰定义？范围内与范围外是否明确？ |
    | 用户场景 | 是否覆盖了所有用户场景？是否有遗漏的用户角色或交互路径？ |
    | 业务规则 | 业务规则是否一致？规则之间是否存在矛盾？ |
    | 异常流程 | 错误/异常流程是否已记录？边界情况是否已考虑？ |
    | 验收标准 | 验收标准是否可测试且具体？能否被验证？ |
    | 隐含假设 | 隐藏的假设是否已被发现并明确说明？ |
    | 完整性 | TODO 标记、占位符、"TBD"、未完成的章节 |
    | 清晰度 | 模糊的描述、未定义的含糊术语 |

    ## 校准标准

    **仅标记会在设计或实现阶段造成实际问题的问题。**
    遗漏的维度、矛盾的业务规则、或模糊到无法测试的验收标准——这些是问题。
    措辞微调、风格偏好、以及"某些章节不如其他章节详细"不是问题。

    除非存在会导致设计缺陷的严重缺口，否则应予以通过。

    ## 输出格式

    ## 需求审查

    **状态：** ✅ 通过 | ❌ 存在问题

    **问题（如有）：**
    - [章节 X]：[具体问题] - [影响原因]

    **建议（仅供参考）：**
    - [不阻塞通过的改进建议]
```

**审查员返回：** 状态、问题（如有）、建议
