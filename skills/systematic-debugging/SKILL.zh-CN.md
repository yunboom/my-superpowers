# 系统性调试

## 概述

随机修复浪费时间并引入新 bug。快速补丁掩盖了底层问题。

**核心原则：** 在尝试修复之前，始终先找到根本原因。治标不治本就是失败。

**违反此流程的字面意思就是违反调试的精神。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

如果你没有完成阶段 1，你不能提出修复方案。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产环境 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况使用：**
- 时间紧迫（紧急情况让猜测变得诱人）
- "只是一个快速修复"看起来很明显
- 你已经尝试了多次修复
- 前一次修复没有生效
- 你没有完全理解问题

**不要在以下情况跳过：**
- 问题看起来简单（简单的 bug 也有根本原因）
- 你很着急（赶时间保证返工）
- 经理要求立刻修复（系统性方法比盲目尝试更快）

## 四个阶段

你必须完成每个阶段后才能进入下一个。

### 阶段 1：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误代码

2. **一致地复现**
   - 能否可靠地触发它？
   - 确切的步骤是什么？
   - 每次都会发生吗？
   - 如果无法复现 → 收集更多数据，不要猜测

3. **检查最近的变更**
   - 什么变更可能导致了这个问题？
   - Git diff，最近的提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → build → signing，API → service → database）：**

   **在提出修复之前，添加诊断检测：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这能揭示：** 哪一层失败了（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误深在调用栈中时：**

   参见本目录中的 `root-cause-tracing.md` 了解完整的反向追踪技术。

   **简要版：**
   - 错误值的来源在哪里？
   - 谁用错误值调用了这里？
   - 持续向上追踪直到找到源头
   - 在源头修复，而不是在症状处

### 阶段 2：模式分析

**在修复之前找到模式：**

1. **找到工作正常的示例**
   - 在同一代码库中找到类似的正常工作代码
   - 什么类似的东西是正常工作的？

2. **与参考实现对比**
   - 如果实现某个模式，完整阅读参考实现
   - 不要略读——逐行阅读
   - 在应用之前完全理解该模式

3. **识别差异**
   - 正常工作的和异常的之间有什么不同？
   - 列出每一个差异，无论多小
   - 不要假设"那不可能有关系"

4. **理解依赖**
   - 这需要哪些其他组件？
   - 什么设置、配置、环境？
   - 它做了什么假设？

### 阶段 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清楚陈述："我认为 X 是根本原因，因为 Y"
   - 把它写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 做出最小的可能变更来测试假设
   - 一次只改一个变量
   - 不要同时修复多个东西

3. **继续之前先验证**
   - 有效了？是 → 阶段 4
   - 没有效？形成新假设
   - 不要在上面叠加更多修复

4. **当你不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 做更多研究

### 阶段 4：实现

**修复根本原因，而不是症状：**

1. **创建失败的测试用例**
   - 最简单的可能复现
   - 如果可能则使用自动化测试
   - 如果没有框架则使用一次性测试脚本
   - 修复之前必须有
   - 使用 `superpowers:test-driven-development` skill 编写正确的失败测试

2. **实现单一修复**
   - 解决已识别的根本原因
   - 一次只做一个变更
   - 不要"顺便"改进
   - 不要捆绑重构

3. **验证修复**
   - 测试现在通过了？
   - 没有其他测试被破坏？
   - 问题确实解决了？

4. **如果修复不起作用**
   - 停下来
   - 数一下：你已经尝试了多少次修复？
   - 如果 < 3 次：回到阶段 1，用新信息重新分析
   - **如果 ≥ 3 次：停下来质疑架构（见下方步骤 5）**
   - 在进行架构讨论之前不要尝试第 4 次修复

5. **如果 3 次以上修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每次修复都在不同地方暴露新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实现
   - 每次修复在其他地方产生新的症状

   **停下来质疑基本面：**
   - 这个模式从根本上是否合理？
   - 我们是否"纯粹因为惯性而坚持"？
   - 应该重构架构还是继续修复症状？

   **在尝试更多修复之前与你的人类伙伴讨论**

   这不是假设失败——这是架构有误。

## 危险信号 - 停下来遵循流程

如果你发现自己在想：
- "先临时修一下，之后再调查"
- "试着改改 X 看看能不能行"
- "加几个修改，跑一下测试"
- "跳过测试，我手动验证"
- "大概是 X，让我修一下"
- "我不完全理解但这可能行"
- "模式说的是 X 但我要做不同的调整"
- "以下是主要问题：[在没有调查的情况下列出修复方案]"
- 在追踪数据流之前提出解决方案
- **"再试一次修复"（已经尝试了 2 次以上）**
- **每次修复都在不同地方暴露新问题**

**以上所有都意味着：停下来。回到阶段 1。**

**如果 3 次以上修复失败：** 质疑架构（见阶段 4.5）

## 你的人类伙伴暗示你做错了的信号

**注意以下纠正：**
- "那不是没有发生吗？" - 你没有验证就做了假设
- "它能告诉我们……？" - 你应该添加证据收集
- "不要猜" - 你在没有理解的情况下提出修复
- "深入思考这个" - 质疑基本面，而不仅仅是症状
- "我们卡住了？"（沮丧） - 你的方法不奏效

**当你看到这些时：** 停下来。回到阶段 1。

## 常见的自我合理化

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单的问题也有根本原因。对简单 bug，流程很快。 |
| "紧急情况，没时间走流程" | 系统性调试比猜测-检查的反复折腾更快。 |
| "先试这个，然后再调查" | 第一次修复设定了模式。从一开始就做对。 |
| "确认修复有效后再写测试" | 未经测试的修复不可靠。先写测试证明它有效。 |
| "同时修多个问题更省时" | 无法隔离哪个有效。会引入新 bug。 |
| "参考文档太长，我改编一下模式" | 不完全理解保证出 bug。完整阅读。 |
| "我看到了问题，让我修它" | 看到症状 ≠ 理解根本原因。 |
| "再试一次修复"（已经失败 2 次以上） | 3 次以上失败 = 架构问题。质疑模式，不要再次修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|----------|----------|
| **1. 根本原因** | 阅读错误、复现、检查变更、收集证据 | 理解是什么以及为什么 |
| **2. 模式** | 找到工作正常的示例、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或新假设 |
| **4. 实现** | 创建测试、修复、验证 | Bug 解决，测试通过 |

## 当流程揭示"没有根本原因"时

如果系统性调查揭示问题确实是环境相关、时序相关或外部原因：

1. 你已完成流程
2. 记录你调查了什么
3. 实现适当的处理（重试、超时、错误消息）
4. 添加监控/日志以便未来调查

**但是：** 95% 的"没有根本原因"案例是调查不充分。

## 辅助技术

这些技术是系统性调试的一部分，可在本目录中找到：

## 实际影响

来自调试会话的数据：
- 系统性方法：15-30 分钟修复
- 随机修复方法：2-3 小时的反复折腾
- 首次修复成功率：95% 对比 40%
- 引入新 bug：几乎为零 对比 常见
